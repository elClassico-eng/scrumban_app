# Учебный разбор диаграммы классов

Этот документ — гайд для понимания того, что такое class diagram, зачем она нужна и как читать ту, что мы сделали для диплома. Читается вместе с 4 простыми SVG-диаграммами в этой папке.

> **Цель:** после прочтения ты должен уметь:
> 1. Объяснить, что такое класс, атрибут, операция.
> 2. Читать связи между классами: что такое ассоциация, композиция, кратность.
> 3. Смотреть на полную диаграмму `../domain-classes.svg` и понимать, что на ней нарисовано.

## Зачем нужна диаграмма классов

Class diagram показывает **из чего состоит наша система на уровне данных**:
- какие есть основные "вещи" (классы / сущности);
- какие у них свойства (атрибуты);
- как они связаны между собой.

Это **скелет модели данных**. Позже он превращается в:
- **таблицы БД** — Drizzle SQL-миграции в `drizzle/migrations/` + текстовое описание в [`../../../07-domain-model.md`](../../../07-domain-model.md);
- **TypeScript-типы** в Drizzle schema (`server/db/schema.ts`);
- **TypeScript-типы** на фронтенде через openapi-typescript (`shared/types/api.d.ts`).

Так что class diagram — это **документ-контракт**: все три (БД, бэк, фронт) должны отражать одну модель.

## Шаг 1 — Один класс

**Файл:** [`01-один-класс.svg`](01-один-класс.svg) • исходник [`01-один-класс.puml`](01-один-класс.puml)

На этом шаге — один класс `User`. Посмотри на диаграмму: прямоугольник поделён горизонтальными линиями на 3 секции:

1. **Имя класса** — `User` (сверху).
2. **Атрибуты** — `id`, `email`, `name`, `createdAt`. Это данные, которые есть у каждого пользователя.
3. **Операции** — `login(...)`, `logout()`. Это то, что объект класса умеет делать.

### Синтаксис атрибутов
```
+ id : UUID
```
- `+` — видимость (public = доступно снаружи);
- `id` — имя;
- `UUID` — тип.

### Видимость (visibility)
| Символ | Что означает |
|--------|--------------|
| `+`    | public — можно читать/менять извне |
| `-`    | private — только внутри класса |
| `#`    | protected — доступно в наследниках |

В нашем проекте в доменной модели почти всё `+` (публичное), потому что это данные, с которыми работают разные слои приложения.

### Типы
- `UUID` — универсально уникальный идентификатор (16 байт, выглядит как `a3f1b9-2c...-xxx`). Используется везде как id.
- `text` — строка.
- `DateTime` — время (в коде — `timestamptz` в БД, `time.Time` в Go).
- `int`, `decimal`, `bool` — числа и логический тип.
- Тип с `?` в конце (например, `closedAt : DateTime?`) — **nullable**, может отсутствовать (NULL в БД, указатель `*time.Time` в Go).

### Связь с нашим кодом
Класс `User` превратится в:
- Таблицу `users` в PostgreSQL (см. [`../../../07-domain-model.md#users`](../../../07-domain-model.md)).
- Go-структуру в файле `internal/domain/user.go`.
- TypeScript-интерфейс в `frontend/lib/api/types.ts` (генерируется из OpenAPI).

## Шаг 2 — Ассоциация между классами

**Файл:** [`02-ассоциация.svg`](02-ассоциация.svg) • [`02-ассоциация.puml`](02-ассоциация.puml)

Два класса — `User` и `Session` — соединены простой линией. Это **ассоциация** — самый частый вид связи.

### Что такое Session
Session — это запись о входе пользователя в систему. Когда user логинится, создаётся Session (с токеном в cookie). Когда он выходит — session удаляется (revoked).

### Кратность (multiplicity)
На концах линии — цифры:
- `"1"` на стороне User означает: **у одной Session всегда ровно ОДИН пользователь.** (Сессия не может быть без юзера.)
- `"0..*"` на стороне Session означает: **у одного User может быть НОЛЬ ИЛИ МНОГО сессий.**

Пример:
- User не зашёл никуда → 0 сессий.
- User зашёл на ноуте → 1 сессия.
- User зашёл на ноуте, на телефоне и на рабочем компьютере → 3 сессии.

### Шпаргалка по кратностям

| Запись | Значение | Пример |
|--------|----------|--------|
| `1`    | ровно один (обязательно) | У каждой Session — один User |
| `0..1` | ноль или один (опционально) | У Task может быть один assignee или ни одного |
| `0..*` | ноль или много | У User может быть много сессий |
| `1..*` | один или много (минимум один) | У Workspace минимум один member (owner) |
| `*`    | то же, что `0..*`, просто короче | |

### Направление чтения
Стрелочка `>` рядом с подписью "has" на линии означает: читать **слева направо** — "**User has Session**".

## Шаг 3 — Композиция vs Ассоциация

**Файл:** [`03-композиция.svg`](03-композиция.svg) • [`03-композиция.puml`](03-композиция.puml)

Здесь два примера связей:

### Композиция (Board → Column)
- Обозначение: линия с **закрашенным ромбом** на стороне "целого" (Board).
- Семантика: **Column — часть Board, не может существовать без него.**
- Если удалить Board, все его Column должны удалиться автоматически (каскад).
- В БД — это `ON DELETE CASCADE` на foreign key.

### Ассоциация (Task ↔ User как assignee)
- Обозначение: обычная линия.
- Семантика: **Task существует независимо от User.**
- Если User удалится, Task останется — просто assignee станет `null`.
- В БД — это `ON DELETE SET NULL` или отсутствие FK каскада.

### Агрегация (для справки, в нашем коде не используется)
- Обозначение: линия с **пустым (незакрашенным) ромбом**.
- Это **слабая** форма композиции. "Целое ссылается на часть, но часть может жить и без целого."
- На практике ассоциация и агрегация часто взаимозаменяемы; композиция — отдельный чёткий случай.
- **В нашем коде мы явно используем только композицию и ассоциацию.**

### Практический вопрос
Как решить, что использовать?

1. **Композиция** — если "часть" осмысленна только внутри "целого". Пример: Column без Board — бессмыслица.
2. **Ассоциация** — если оба могут жить независимо. Пример: Task может быть с assignee или без.

### Наши композиции в проекте
- `Workspace *-- Project` — проекты уходят с workspace.
- `Project *-- Board` — у проекта своя доска.
- `Board *-- Column` — колонки принадлежат доске.
- `Project *-- Sprint` — спринты проекта.
- `Task *-- TaskComment / TaskTag / TaskAttachment` — вложенные сущности.

### Наши ассоциации
- `Task -- User` (assignee, reporter) — пользователи существуют отдельно.
- `Task -- Sprint` — задача может быть в бэклоге без спринта.

## Шаг 4 — Полный пример (связующий класс + enum)

**Файл:** [`04-полный-пример.svg`](04-полный-пример.svg) • [`04-полный-пример.puml`](04-полный-пример.puml)

Здесь три класса + один enum:

### Связующий класс (WorkspaceMember)
Когда между двумя классами нужна связь **"многие ко многим"**, и у этой связи есть свои атрибуты — используют "связующий" (association class).

Пример: User и Workspace.
- Один User может быть в нескольких Workspace.
- Один Workspace содержит много User.
- Для каждой пары (User, Workspace) нужны свои данные: `role` (какую роль имеет), `joinedAt` (когда присоединился).

Эти данные **нельзя** хранить в User (они зависят от конкретного Workspace) и нельзя хранить в Workspace (зависят от конкретного User). Они принадлежат **паре**. Поэтому мы создаём третий класс — **WorkspaceMember** — который хранит именно эти пары.

В БД это таблица с **композитным первичным ключом** `(workspace_id, user_id)` — это гарантирует, что один user может быть в одном workspace ровно с одной ролью.

### Enum (перечисление)
На диаграмме есть отдельный блок `<<enumeration>> Role` со значениями `OWNER`, `ADMIN`, `MEMBER`, `VIEWER`. Это **перечисление** — список допустимых значений для поля `role` в `WorkspaceMember`.

Если тип поля — enum, значение **может быть только одним из перечисленных**, никакие другие не допустимы. В БД это реализуется как:
```sql
role TEXT NOT NULL CHECK (role IN ('owner','admin','member','viewer'))
```

В Go — как набор констант:
```go
type Role string
const (
    RoleOwner  Role = "owner"
    RoleAdmin  Role = "admin"
    RoleMember Role = "member"
    RoleViewer Role = "viewer"
)
```

### Конкретный пример данных

Представь, что у нас такие записи:

**users:**
| id | email |
|----|-------|
| A  | danya@example.com |
| B  | alex@example.com |

**workspaces:**
| id | name |
|----|------|
| X  | Scrumban Team |
| Y  | Pet Projects |

**workspace_members:**
| workspace_id | user_id | role | joinedAt |
|--------------|---------|------|----------|
| X            | A       | OWNER | 2026-01-15 |
| X            | B       | ADMIN | 2026-02-01 |
| Y            | A       | MEMBER| 2026-03-10 |

Читаем:
- User A владеет Workspace X (owner) и участвует в Workspace Y как обычный member.
- User B — admin в Workspace X, в Workspace Y его нет.

Когда A откроет приложение, он увидит 2 workspace в списке (X и Y). В X у него будут все кнопки admin-панели; в Y — только работа с задачами.

## Что дальше

После этого 4-шагового разбора ты должен уверенно читать:

1. **Полную диаграмму** [`../domain-classes.svg`](../domain-classes.svg) — там всё, что для диплома.
2. **Текст описания** [`../domain-classes.md`](../domain-classes.md).

Когда откроешь полную диаграмму, ищи на ней:
- Классы (прямоугольники с 2–3 секциями).
- Enum'ы (обычно рамкой с подписью `<<enumeration>>`).
- Связи: композиция (закрашенный ромб) и ассоциация (обычная линия).
- Кратности (`1`, `0..*`, ...) на концах линий.
- Стереотипы в кавычках-шевронах: `<<tenant root>>` на Workspace, `<<append-only>>` на Event.

## Шпаргалка для защиты

- **"Почему Event отдельный класс?"** — Append-only журнал, источник аналитики. Нельзя ни менять, ни удалять события.
- **"Почему у Task nullable sprint_id?"** — Задача может быть в бэклоге (вне любого спринта). Это ключевое отличие Scrumban от чистого Scrum.
- **"Зачем отдельный класс WorkspaceMember?"** — Хранит не только связь User↔Workspace, но и её атрибуты: роль, дата вступления.
- **"Что такое composition?"** — Часть не может жить без целого. У нас так связаны Board↔Column: колонки бессмысленны без доски.
- **"Почему енумы вынесены отдельно?"** — Это типы значений для полей. Повышает читаемость диаграммы и согласованность: одни и те же значения используются и в БД (`CHECK`), и в коде.

## Глоссарий для быстрого поиска

| Термин | Перевод / пояснение |
|--------|---------------------|
| **Class** | Класс — шаблон объекта (User, Task, ...) |
| **Attribute** | Атрибут — поле-данные класса (email, title) |
| **Operation / Method** | Операция/метод — что класс умеет делать |
| **Association** | Ассоциация — обычная связь между классами |
| **Multiplicity** | Кратность — цифры на концах связи (`1`, `0..*`) |
| **Composition** | Композиция — сильная связь "часть-целое", закрашенный ромб |
| **Aggregation** | Агрегация — слабая форма композиции, пустой ромб |
| **Generalization** | Обобщение / наследование (в доменной модели не используется) |
| **Enumeration / Enum** | Перечисление — список допустимых значений |
| **Stereotype** | Стереотип — метка в `<<...>>`, особый тип элемента |
| **Association class** | Связующий класс — для связи многие-ко-многим с атрибутами |

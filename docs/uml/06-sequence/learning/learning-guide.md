# Учебный разбор Sequence диаграммы

Sequence diagram показывает **взаимодействие между компонентами/объектами во времени**. Это главный инструмент для описания «как работает» тот или иной сценарий.

> **Цель:** научиться читать наши 3 диплом-диаграммы ([login, create-task-sse, monte-carlo](../)) и объяснять, что в них происходит.

## Зачем нужна Sequence diagram

Use case говорит «что делает» система. Sequence — **«как именно делает»**, шаг за шагом во времени.

Идёт в главу диплома **«Реализация»** или «Описание ключевых сценариев».

Обычно в дипломе **2–4 sequence-диаграммы** на самые важные сценарии, а не «для каждого прецедента». У нас — 3: вход, создание задачи с broadcast, Monte Carlo расчёт.

## Шаг 1 — Один вызов

**Файл:** [`01-один-вызов.puml`](01-один-вызов.puml)

Минимальный пример: пользователь кликнул, браузер показал форму.

### Ключевые элементы
- **Участник (participant)** — прямоугольник сверху + вертикальная пунктирная линия (**lifeline**, линия жизни). Это может быть: человек (actor), браузер, сервер, БД, внешний сервис.
- **Время идёт сверху вниз.** Первое действие — сверху, последующие — ниже.
- **Стрелки между lifeline'ами** = сообщения.

### Типы стрелок
- **`→` сплошная с закрытой головкой** — синхронный вызов (отправитель ждёт ответа).
- **`⇢` пунктирная** — возврат (return), результат.
- **`→` сплошная с открытой головкой** — асинхронный вызов (fire-and-forget).

## Шаг 2 — Цепочка вызовов

**Файл:** [`02-цепочка-вызовов.puml`](02-цепочка-вызовов.puml)

Классический CRUD-флоу: User → Browser → Backend → DB и обратно.

### Что нового
- **Activation bars** (чёрные прямоугольники на lifeline). Показывают, когда участник **активен** — то есть обрабатывает запрос или ждёт ответа.
- Несколько уровней вложенности (Backend ждёт ответ от DB, Browser ждёт ответ от Backend).

### Как читать
Сверху вниз: каждое действие — это одна стрелка. Подписи описывают, что происходит.

Пример:
1. User кликает в Browser.
2. Browser шлёт POST на Backend.
3. Backend делает INSERT в БД.
4. БД возвращает id созданной записи.
5. Backend возвращает 201 с данными.
6. Browser обновляет UI.

## Шаг 3 — Условное ветвление через `alt`

**Файл:** [`03-alt-фрагмент.puml`](03-alt-фрагмент.puml)

Фрагмент `alt` — это **if/else** на диаграмме. Рисуется рамкой вокруг нескольких возможных веток.

### Синтаксис
```
alt условие 1
    ... действия если 1
else условие 2
    ... действия если 2
end
```

Только одна ветка выполняется — в зависимости от условия.

### Типичные фрагменты

| Фрагмент | Что означает | Когда используется |
|----------|--------------|---------------------|
| `alt` | if/else (ветвление) | Разные исходы (успех/ошибка) |
| `opt` | опциональное выполнение | Действие может быть, а может не быть |
| `loop` | цикл | Повторяется несколько раз |
| `par` | параллельно | Несколько веток одновременно |
| `break` | прерывание | Выход из цикла или sequence'а |

### В нашем login-флоу
Три исхода:
1. User не найден → 401.
2. User найден, но пароль неверен → 401.
3. User найден, пароль верен → 200 + cookie.

Оборачиваем всё это в `alt` — получаем чистую диаграмму.

## Шаг 4 — Параллельное выполнение через `par`

**Файл:** [`04-par-параллельность.puml`](04-par-параллельность.puml)

Когда одно событие запускает **несколько параллельных реакций**, используется `par`.

### В нашем проекте
Самый яркий пример — event-driven модель. Когда Backend публикует событие (`task_moved`):
- SSE Hub рассылает подписчикам (real-time UI обновляется).
- Worker ставит фоновую задачу (отправка в Telegram).
- Аналитический агрегатор обновляет `flow_daily`.

Всё это — **одновременно и независимо**. `par` в диаграмме показывает именно эту одновременность.

### Почему это важно
Если бы всё было последовательно, Backend ждал бы сначала SSE-рассылку, потом отправку в Telegram, потом пересчёт. Это было бы медленно. Параллельность ускоряет работу пользователя (он получает 200 сразу, не дожидаясь всех побочных эффектов).

## Теперь — наши три диплом-диаграммы

Открывай в IDE:

### [`../login.puml`](../login.puml)
- Участники: User, Browser, Caddy, HTTP API, AuthN Middleware, Auth Service, Storage, PostgreSQL.
- `alt` с тремя ветками (not found / wrong password / success).
- Создание session: random token → hash → store in DB → cookie.

### [`../create-task-sse.puml`](../create-task-sse.puml)
- Два разных пользователя (A создаёт, B наблюдает).
- Предусловие: B уже подключён к SSE-потоку.
- `par`-фрагмент с параллельными реакциями.
- Optimistic UI на стороне Browser A.

### [`../monte-carlo.puml`](../monte-carlo.puml)
- Cache LRU (проверка кэша перед расчётом).
- `alt` с веткой cache hit / cache miss.
- Min-data threshold (не считаем MC при <3 спринтов).
- Само ядро симуляции (1000 итераций, семплирование из эмпирического распределения).

## Возможные вопросы на защите

1. **«Зачем activation bars, не всё ли равно?»**
   «Они показывают, когда участник активен — то есть обрабатывает запрос или ждёт ответа. Это критично для понимания latency и race conditions в реальном коде».

2. **«Почему используется `par`, а не просто последовательные вызовы?»**
   «Потому что event-driven модель: одно событие → много реакций одновременно. Параллельность даёт низкую latency пользователю (он не ждёт всех побочных эффектов) и отказоустойчивость (падение одного обработчика не ломает другие)».

3. **«Что такое SSE и почему не WebSocket?»**
   «Server-Sent Events — обычный HTTP-стрим с сервера на клиент. Проще, чем WebSocket (нет bidirectional), достаточно для рассылки обновлений доски. См. подробнее в docs/06-system-architecture.md».

4. **«Как обработана ошибка в login?»**
   «Через `alt`-фрагмент. Три возможные ветки, в коде — sentinel error'ы (ErrInvalidCredentials) + httperr helper, который мапит в HTTP-коды (401 / 500)».

5. **«Зачем кэш у Monte Carlo?»**
   «Расчёт 1000 симуляций стоит ~500ms. Если каждый запрос дашборда его делать, это плохо. LRU 15 минут — большинство запросов попадают в кэш, БД не грузим».

## Глоссарий

| Термин | Русское пояснение |
|--------|-------------------|
| **Participant** | Участник — тот, кто обменивается сообщениями |
| **Lifeline** | Линия жизни — вертикальная пунктирная линия под именем участника |
| **Activation bar** | Активация — чёрный прямоугольник на lifeline, показывает «занят» |
| **Synchronous message** | Синхронное сообщение — отправитель ждёт ответа |
| **Asynchronous message** | Асинхронное — fire-and-forget |
| **Return message** | Возврат — пунктирная стрелка ответа |
| **Fragment** | Фрагмент — рамка вокруг группы действий (alt, opt, loop, par) |
| **`alt`** | Альтернатива — ветвление по условиям |
| **`par`** | Параллельные ветки |
| **`opt`** | Опциональное выполнение |
| **`loop`** | Цикл |
| **Guard** | Условие в квадратных скобках, по которому выбирается ветка |

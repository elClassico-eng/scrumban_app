# Учебный разбор State Machine диаграммы

State machine (конечный автомат) описывает **жизненный цикл одного объекта**: какие у него бывают состояния, как он переходит между ними, что происходит в каждом.

> **Цель:** научиться читать наши диплом-диаграммы [`../task-lifecycle.puml`](../task-lifecycle.puml) и [`../sprint-lifecycle.puml`](../sprint-lifecycle.puml).

## Зачем нужна State Machine

Если class/ER/component показывают **структуру** (что есть), а sequence — **взаимодействие** (как работают вместе), то state machine показывает **эволюцию одного объекта во времени**: «Задача живёт, проходя через такие-то состояния».

Используется для сущностей со **сложным жизненным циклом**:
- У нас: Task (много состояний, возвраты, reopens) и Sprint (planned → active → closed).
- Не нужна для простых сущностей (User просто «активен»/«удалён»).

Идёт в главу диплома **«Реализация»** — раздел описания ключевых сущностей.

## Шаг 1 — Простейший автомат

**Файл:** [`01-простой-автомат.puml`](01-простой-автомат.puml)

Два состояния — `Черновик` и `Опубликована` — и переход между ними.

### Ключевые элементы

- **Initial state** (закрашенный чёрный круг) — откуда начинается жизнь объекта. Выход **один**.
- **State** (скруглённый прямоугольник с именем) — одно из возможных «положений».
- **Transition** (стрелка) — переход между состояниями.

В нашем проекте:
- Task может быть: `Backlog`, `In Progress`, `Review`, `Done`, `Archived`.
- Sprint может быть: `Planned`, `Active`, `Closed`.
- User — глобально просто `active` / `deleted`, автомат не нужен.

## Шаг 2 — Переходы с событиями, условиями, действиями

**Файл:** [`02-переходы-с-событиями.puml`](02-переходы-с-событиями.puml)

Подпись на стрелке имеет формат:

```
событие [условие] / действие
```

### Событие (event / trigger)
Что вызывает переход. В нашем коде — обычно вызов функции или получение message'а.

Пример: «опубликовать» (пользователь нажал кнопку Publish).

### Условие в квадратных скобках (guard)
Обязательное условие. Если оно false — переход НЕ произойдёт. Объект останется в исходном состоянии.

Пример: `[title != ""]` — можно опубликовать, только если заголовок не пустой.

### Действие после слэша (action)
Побочный эффект, выполняется при переходе.

Пример: `/ send_notification()` — при переходе к «Опубликована» отправить уведомление.

### Final state
Круг в круге (bullseye). Конечное состояние — объект «умер» (для задач = архивирован, но запись в БД остаётся).

### В нашем проекте
Пример перехода task из Review в Done:
```
approved [reviewer_role >= SM] / event: task_closed, set closed_at
```

Это значит:
- **Событие**: команда «approved» (реcenзент одобрил).
- **Условие**: роль рецензента — минимум SM.
- **Действие**: эмитим событие `task_closed`, ставим `closed_at = now()`.

## Шаг 3 — Entry и Exit действия

**Файл:** [`03-entry-exit-действия.puml`](03-entry-exit-действия.puml)

Внутри состояния можно описать, что делается при входе и выходе:

- **`entry /`** — при входе в состояние. Пример: при входе в `In Progress` — запустить таймер cycle_time.
- **`exit /`** — при выходе. Пример: при уходе из `In Progress` — остановить таймер.
- **`do /`** — в течение (пока в этом состоянии). Редко используется в нашем проекте.

### Зачем это в коде

Вместо того, чтобы разбрасывать побочные эффекты по разным местам кода («при перемещении задачи не забудь обновить таймер, отправить уведомление, записать событие...»), мы **привязываем действия к состояниям**:

```go
func OnTransition(task *Task, oldState, newState State) {
    execExitActions(task, oldState)
    task.State = newState
    execEntryActions(task, newState)
}
```

Получаем:
- **Консистентность**: все побочные эффекты всегда выполняются при переходе.
- **Понятность**: чтобы узнать, что происходит в `Done`, смотришь на entry/exit этого состояния.
- **Тестируемость**: mock'аются отдельно.

### В нашем проекте
Entry-действия в `Done`:
- `set_closed_at()` — фиксируем время закрытия.
- `emit_event(task_closed)` — публикуем событие (запустит пересчёт velocity).

Entry-действия в `Review`:
- `assign_reviewer()` — назначаем рецензента (если нужно).
- `send_notification()` — уведомляем о необходимости ревью.

## Шаг 4 — Полный жизненный цикл задачи

**Файл:** [`04-полный-цикл-задачи.puml`](04-полный-цикл-задачи.puml)

Это упрощённая версия нашей диплом-диаграммы [`../task-lifecycle.puml`](../task-lifecycle.puml).

### Основной флоу (Scrumban happy path)
```
Backlog → In Progress → Review → Done
```

Пользователь создал задачу, начал работать, отправил на ревью, одобрили.

### Отклонения от happy path
- **Review → In Progress** — провал ревью, возврат на доработку. Реальный кейс.
- **In Progress → Backlog** — деприоритизация (приоритеты поменялись).
- **Done → In Progress** — **reopen**, переоткрытие после закрытия. `reopened_count` увеличивается. Это важная метрика качества.

### Archive — из любого состояния
Soft delete. Может быть выполнен из любого состояния: `Backlog`, `In Progress`, `Review`, `Done`. Это не часть основного флоу — административное действие.

## Возможные вопросы на защите

1. **«Почему у задачи отдельный reopened_count?»**
   «Это метрика нестабильности: если задача часто переоткрывается после закрытия — возможно, есть проблема с ревью или с определением готовности. Поле используется в будущей аналитике "flakiness"».

2. **«Почему Review → In Progress в обе стороны?»**
   «Потому что ревью может провалиться — нужна доработка. Это реальный кейс разработки. В метриках cycle time в Review учитывается весь суммарный проход (включая повторные заходы)».

3. **«Что такое entry-actions и зачем они?»**
   «Действия, которые выполняются при входе в состояние. Вместо того чтобы разбросать побочные эффекты по разным местам кода, мы привязываем их к переходам. Упрощает консистентность и тесты».

4. **«Соответствует ли State Machine реальному коду?»**
   «Да. В Go-коде есть функция `TasksService.Move(oldColumn, newColumn)` — она и вызывает exit-actions старой колонки и entry-actions новой. Определяется через `column_role` (enum), которое есть в ER-диаграмме».

5. **«Почему soft delete, не hard?»**
   «Audit trail и возможность восстановления. Жёсткое удаление лишает истории. Archived — терминальное состояние для операций, но запись в БД остаётся».

## Глоссарий

| Термин | Русское пояснение |
|--------|-------------------|
| **State** | Состояние — одно из возможных положений объекта |
| **Initial state** | Начальное — закрашенный чёрный круг, откуда начинается жизнь |
| **Final state** | Конечное — круг в круге, терминальное положение |
| **Transition** | Переход — стрелка между состояниями |
| **Event / Trigger** | Событие, вызывающее переход |
| **Guard** | Условие в `[...]` — переход возможен только при его истинности |
| **Action** | Действие в `/...` — побочный эффект перехода |
| **Entry action** | Действие при входе в состояние |
| **Exit action** | Действие при выходе из состояния |
| **Do activity** | Действие в течение пребывания в состоянии |
| **Composite state** | Составное состояние — включает подсостояния |
| **Self-transition** | Самопереход — из состояния в него же |

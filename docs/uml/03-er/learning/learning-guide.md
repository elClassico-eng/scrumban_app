# Учебный разбор ER-диаграммы

ER (Entity-Relationship) диаграмма — это **физическая схема базы данных**. Она показывает таблицы с точными типами полей, ключами, индексами и связями.

> **Цель:** после прочтения ты должен уметь читать нашу полную ER-диаграмму [`../database.puml`](../database.puml) и понимать, что каждый элемент значит в терминах PostgreSQL.

## Зачем нужна ER-диаграмма

Если class diagram (из папки `../../02-class/`) — это **логическая модель** (сущности, концепции), то ER-диаграмма — **физическая схема**: конкретная реализация этих сущностей в виде таблиц Postgres.

Например: класс `User` превращается в таблицу `users` с конкретными полями типа `uuid`, `text`, `timestamptz`; индексами; foreign key'ами; constraints.

В дипломе ER-диаграмма идёт в главу **«Проектирование базы данных»**.

## Шаг 1 — Одна таблица

**Файл:** [`01-одна-таблица.puml`](01-одна-таблица.puml)

Открой в IDE preview. Видишь рамку `users` с полями внутри.

### Как читать поля

Каждая строка — одно поле таблицы:

```
*id : uuid <<PK>>
```

- `*` (звёздочка слева) — **NOT NULL**, поле обязательное.
- Без звезды — **nullable**, поле может быть пустым (NULL в БД).
- `id` — имя поля.
- `:` — разделитель.
- `uuid` — тип.
- `<<PK>>` справа в «шевронах» — **метка**: в данном случае `PK` = Primary Key (первичный ключ).

Другие метки:
- `<<U>>` = Unique — уникальное значение (два одинаковых email нельзя).
- `<<FK>>` = Foreign Key — внешний ключ (ссылается на id в другой таблице).
- `<<I>>` = Indexed — есть индекс для быстрого поиска.

### Разделитель `--`
В середине таблицы линия. Выше неё — **первичный ключ** (обычно `id`). Ниже — остальные поля. Просто визуальное разделение, не часть синтаксиса БД.

### Типы PostgreSQL, которые встретишь

| Тип | Что хранит | Пример |
|-----|-----------|--------|
| `uuid` | Уникальный ID | `a3f1b9-...` |
| `text` | Строка любой длины | email, name |
| `timestamptz` | Дата+время в UTC | 2026-04-20 12:00:00+00 |
| `int`, `bigint` | Целое число | count, size_bytes |
| `numeric` | Дробное число | story_points, price |
| `boolean` | true/false | is_deleted |
| `jsonb` | JSON, бинарно | payload событий |
| `inet` | IP-адрес | 192.168.0.1 |

## Шаг 2 — Связь через Foreign Key

**Файл:** [`02-связь-через-fk.puml`](02-связь-через-fk.puml)

Здесь две таблицы: `users` и `sessions`. Сессия принадлежит пользователю.

### Foreign Key
В `sessions` есть поле `user_id` с меткой `<<FK>>`. Это **внешний ключ** — ссылается на `users.id`. БД контролирует: ты не можешь вставить в sessions такой `user_id`, которого нет в `users`.

В SQL это выглядит так:
```sql
user_id uuid NOT NULL REFERENCES users(id)
```

### Crow's foot notation (воронья лапка)

Линия между таблицами имеет специальные символы на концах — это **кратность** (cardinality). Нотация называется "crow's foot" из-за похожести на ножку птицы.

**На концах линии:**
- `||` = ровно один (обязательно).
- `|o` = ноль или один.
- `}|` = один или много.
- `}o` = ноль или много.

**Наша связь `users ||--o{ sessions` читается:**
- `||` (у `users`) = «ровно один».
- `o{` (у `sessions`) = «ноль или много».

Перевод: **«У одной sessions ровно один user (обязательно); у одного user может быть 0 или много sessions».**

### Зачем это важно

Из диаграммы сразу видно:
- Можно ли удалить user, у которого есть сессии? (Зависит от каскада: `ON DELETE CASCADE` удалит сессии; `RESTRICT` запретит удалять user).
- Сколько максимум строк в каждой таблице? (users — ограничено числом реальных людей, sessions — гораздо больше).
- Как делать запросы? (Получить все сессии юзера — обычный JOIN).

## Шаг 3 — Композитный ключ и связь N:M

**Файл:** [`03-композитный-ключ.puml`](03-композитный-ключ.puml)

Три таблицы: `users`, `workspaces`, `workspace_members`. Последняя — «связующая» для связи **многие-ко-многим**.

### Многие-ко-многим (N:M)
- Один user может быть в нескольких workspace.
- Один workspace содержит много users.

Так бывает нельзя реализовать двумя FK напрямую. Решение — **связующая таблица**, где каждая строка — одна пара (user, workspace).

### Композитный первичный ключ
В `workspace_members` — **два** `<<PK>>`: `workspace_id` и `user_id`. Это значит, что **пара** полей вместе образует уникальный ключ.

В SQL:
```sql
CREATE TABLE workspace_members (
  workspace_id uuid REFERENCES workspaces(id),
  user_id      uuid REFERENCES users(id),
  role         text NOT NULL,
  joined_at    timestamptz NOT NULL,
  PRIMARY KEY (workspace_id, user_id)
);
```

**Что даёт:** пользователь не может быть в одном и том же workspace дважды (бессмысленно бы было). Но в одном workspace — много записей (по одной на каждого user), и один user может быть во многих workspace.

### Дополнительные данные на связи
На `workspace_members` кроме id-пары есть `role` и `joined_at`. Это данные, которые **относятся к конкретной паре** (user X в workspace Y имеет роль admin), а не к user или workspace отдельно. Поэтому они живут в связующей таблице.

## Шаг 4 — Индексы и Row-Level Security

**Файл:** [`04-индексы-и-rls.puml`](04-индексы-и-rls.puml)

Одна таблица `tasks` с пометкой `<<RLS>>` и индексами.

### Row-Level Security (RLS)
Пометка `<<RLS>>` наверху — это **защита на уровне БД**, включённая в PostgreSQL.

**Зачем:** у нас SaaS с много workspace'ами в одной БД. Если разработчик забудет добавить `WHERE workspace_id = ...`, данные одного клиента попадут другому. **RLS закрывает эту дыру на уровне БД** — Postgres сам добавит условие.

Включается в миграции:
```sql
ALTER TABLE tasks ENABLE ROW LEVEL SECURITY;

CREATE POLICY tasks_isolation ON tasks
  USING (workspace_id = current_setting('app.workspace_id', true)::uuid);
```

После этого любой SELECT/UPDATE/DELETE автоматически фильтруется по `app.workspace_id`, которое устанавливается middleware в начале транзакции.

### Индексы

**Индекс (I)** = специальная структура, ускоряющая поиск. Аналогия — алфавитный указатель в книге: чтобы найти слово, не листаешь всю книгу.

Что индексируем:
- Поля, по которым часто ищем (`workspace_id`, `project_id`, `assignee_id`).
- Поля для сортировки (`created_at DESC`).

### Composite index
Индекс по **нескольким полям вместе**. В примере:
```
I (workspace_id, created_at DESC)
```

Используется для запроса «покажи все задачи workspace X, отсортировано по времени создания».

**Наше архитектурное правило**: все composite-индексы начинаются с `workspace_id`. Это согласовано с RLS: после RLS-фильтрации Postgres использует именно этот индекс эффективно.

### Composite unique constraint

```
U (workspace_id, project_id, short_id)
```

Два-три поля вместе должны быть уникальны. В примере: в **одном проекте** не может быть двух задач с одинаковым `short_id` («SCB-42»). Но в разных проектах — можно («SCB-42» в одном проекте и «PROJ-42» в другом — разные).

Это даёт человекочитаемые ID задач.

## Возможные вопросы на защите

1. **«Почему `sprint_id` в tasks nullable?»**
   «Задача может быть в бэклоге, вне любого спринта. Это ключевое отличие Scrumban от чистого Scrum — беклог живёт отдельно».

2. **«Зачем composite PK на `workspace_members`?»**
   «Чтобы пользователь не мог быть в одном workspace дважды. Пара (workspace_id, user_id) уникальна — максимум одна запись на пару».

3. **«Что даёт RLS?»**
   «Страховку от человеческих ошибок. Даже если в коде забыть WHERE workspace_id, Postgres автоматически отфильтрует по текущему контексту. Защита tenant-изоляции на уровне БД».

4. **«Почему composite-индексы начинаются с workspace_id?»**
   «Согласованность с RLS. После автоматической RLS-фильтрации планировщик Postgres эффективно использует такие индексы. Обратный порядок дал бы worst case».

5. **«Зачем поле `short_id` в tasks, если есть uuid `id`?»**
   «UUID неудобен для людей (длинный, не читается). `short_id` — это "SCB-42", генерируется из project.key + счётчик в проекте, виден в UI и в ссылках».

## Глоссарий

| Термин | Перевод / пояснение |
|--------|---------------------|
| **Entity** | Сущность / таблица |
| **Attribute / Column** | Атрибут / столбец |
| **Primary Key (PK)** | Первичный ключ — уникальный идентификатор строки |
| **Foreign Key (FK)** | Внешний ключ — ссылается на PK другой таблицы |
| **Unique (U)** | Уникальное ограничение — значения не повторяются |
| **Index (I)** | Индекс — для ускорения поиска и сортировки |
| **Composite key** | Составной ключ — из нескольких полей |
| **NOT NULL** | Обязательное поле |
| **Nullable** | Поле может быть пустым (NULL) |
| **Cardinality** | Кратность — сколько строк в одной связаны со сколькими в другой |
| **Crow's foot** | Нотация connectivity на ER-диаграммах |
| **RLS** | Row-Level Security — защита данных на уровне строк |
| **N:M / Many-to-many** | Многие-ко-многим — нужна связующая таблица |
| **Associative entity** | Связующая сущность (для N:M) |

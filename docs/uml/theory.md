# Теория UML — справочник по 14 типам диаграмм

Краткий обзор типов UML 2.5 диаграмм: что показывает, когда используется, примеры. Материал подходит для включения в главу диплома «Анализ методов моделирования» или «Обзор инструментов проектирования».

## Классификация UML 2.5

UML 2.5 определяет **14 типов диаграмм**, разделённых на две категории:

### Структурные диаграммы (7)
Описывают **статическую** структуру системы: из каких частей состоит и как они связаны.

| Тип | Что показывает | Использование |
|-----|----------------|---------------|
| **Class** | Классы, атрибуты, операции, связи (ассоциация, агрегация, композиция, наследование) | Обязательная, любой ОО-проект |
| **Object** | Снимок конкретных объектов в момент времени | Редко, для сложных иллюстраций |
| **Package** | Пакеты и зависимости между ними | При сложной модульной структуре |
| **Composite Structure** | Внутренняя структура класса/компонента, порты и соединители | При иерархической композиции |
| **Component** | Компоненты системы и их интерфейсы | Обязательная, для архитектуры |
| **Deployment** | Физические узлы, артефакты, каналы | Обязательная при развёртывании |
| **Profile** | Расширения UML для доменной области | Редко, требует понимания стереотипов |

### Поведенческие диаграммы (7)
Описывают **динамику** системы: как объекты взаимодействуют во времени.

| Тип | Что показывает | Использование |
|-----|----------------|---------------|
| **Use Case** | Актёры, прецеденты, границы системы | Обязательная, первый этап анализа |
| **Activity** | Поток управления, бизнес-процессы | Для сложных процессов |
| **State Machine** | Состояния объекта и переходы | Для сущностей со сложным lifecycle |
| **Sequence** | Временной порядок сообщений между объектами | Обязательная, для ключевых сценариев |
| **Communication** | То же, что sequence, но акцент на связях | Альтернатива sequence |
| **Interaction Overview** | Граф из sequence-фрагментов | Редко |
| **Timing** | Временны́е ограничения, реакция в реальном времени | Для real-time систем |

## Подробно — диаграммы, которые используются в Scrumban-работе

### 1. Use Case Diagram (диаграмма прецедентов)

**Что показывает:** функциональные требования системы с точки зрения пользователя.

**Элементы:**
- **Актёры** — сущности, взаимодействующие с системой (люди, внешние системы, планировщики).
- **Прецеденты (use case)** — функции системы, полезные для актёра.
- **Границы системы** — прямоугольник вокруг прецедентов.
- **Ассоциации** — линии «актёр ↔ прецедент».
- **`<<include>>`** — один прецедент всегда вызывает другой (например, Create Task → Validate Input).
- **`<<extend>>`** — опциональное расширение поведения (например, Move Task → Send Notification).
- **Обобщение актёров** — один актёр наследует возможности другого (Admin наследует всё от Member).

**Когда рисовать:** первой, на этапе анализа требований.

**В нашей работе:** роли Workspace Owner, Admin, Scrum Master, Team Member, Viewer + внешние системы (Git, SMTP, Bot, Scheduler).

### 2. Class Diagram (диаграмма классов)

**Что показывает:** статическую структуру системы в терминах классов.

**Элементы:**
- **Класс** — прямоугольник с тремя секциями: имя / атрибуты / операции.
- **Ассоциация** — линия между классами (направленная, с кратностью `1`, `*`, `0..1`, и т. п.).
- **Агрегация** — ромб «пустой» (слабая связь, объект может жить без контейнера).
- **Композиция** — ромб «закрашенный» (сильная связь, объект умирает с контейнером).
- **Наследование** — треугольная стрелка.
- **Реализация интерфейса** — пунктирная стрелка с треугольником.

**Когда рисовать:** на этапе проектирования доменной модели.

**В нашей работе:** классы User, Workspace, Project, Board, Column, Task, Sprint, Event — с кратностями и связями между ними.

### 3. ER (Entity-Relationship)

**Что показывает:** физическую схему БД.

**Формально не UML**, но традиционно входит в дипломные работы. В PlantUML есть специальный синтаксис (`entity` blocks) или используют `class` с пометкой `<<table>>`.

**Элементы:**
- **Сущности** (таблицы) с полями и типами.
- **Первичные ключи (PK)** и **внешние ключи (FK)**.
- **Связи** с кратностью (1:1, 1:N, N:M).

**Отличие от class diagram:** ER описывает физику хранения (точные типы Postgres, индексы, constraint'ы), class — логическую модель.

### 4. Component Diagram

**Что показывает:** крупные блоки программной системы и их взаимодействие.

**Элементы:**
- **Компонент** — прямоугольник с иконкой `<<component>>`.
- **Интерфейсы** — круг (предоставляемый) / полукруг (требуемый).
- **Порты** — квадраты на границе компонента.
- **Ассоциации** — линии между интерфейсами.

**Когда рисовать:** после use case, для обзора архитектуры.

**В нашей работе:** Nuxt 4 SPA, Nitro server, PostgreSQL, Object Storage, Caddy, внешние сервисы.

### 5. Deployment Diagram

**Что показывает:** физические узлы (серверы, контейнеры, VM) и развёрнутые на них артефакты.

**Элементы:**
- **Узел** — куб (`node`), представляет физическое или виртуальное окружение.
- **Артефакт** — файл, Docker-образ, jar/binary.
- **Коммуникация** — линии между узлами с обозначением протокола (HTTPS, SQL, S3).

**Когда рисовать:** ближе к концу, для главы «Развёртывание».

**В нашей работе:** две диаграммы — SaaS (одна VM на Yandex Cloud) и On-prem (клиентская инфраструктура).

### 6. Sequence Diagram

**Что показывает:** временной порядок обмена сообщениями между объектами.

**Элементы:**
- **Lifeline** — вертикальная линия под именем участника.
- **Activation bar** — прямоугольник на lifeline, показывает «активный» период.
- **Сообщения** — стрелки между lifelines (sync — сплошная, async — открытая).
- **Фрагменты** (`alt`, `opt`, `loop`, `par`) — управляющие структуры.

**Когда рисовать:** для ключевых сценариев, обычно 2–4 на проект.

**В нашей работе:** 
1. Login + создание сессии.
2. Создание задачи с broadcast через SSE другим подписчикам.
3. Расчёт Monte Carlo прогноза для активного спринта.

### 7. State Machine Diagram

**Что показывает:** конечный автомат — состояния объекта и переходы.

**Элементы:**
- **Состояния** — скруглённые прямоугольники.
- **Initial state** — закрашенный кружок (стартовое).
- **Final state** — кружок в кружке (финальное).
- **Переходы** — стрелки с триггерами / условиями / действиями: `event [guard] / action`.

**Когда рисовать:** для сущностей со сложным lifecycle.

**В нашей работе:**
1. **Task state machine** — backlog → in_progress → review → done → archived (с возможным reopened).
2. **Sprint state machine** — planned → active → closed.

## Использование в тексте диплома

### Глава «Анализ требований»
Use Case диаграмма + таблица прецедентов с кратким описанием каждого. Обычно 1–2 страницы.

### Глава «Проектирование»
Class diagram + ER diagram. Текст описывает связи, мощности, ключевые решения (например, «почему Task имеет nullable sprint_id»).

### Глава «Архитектура»
Component diagram. Текст описывает назначение каждого компонента и выбранные интерфейсы.

### Глава «Реализация» / «Работа системы»
Sequence diagram'ы + State machine'ы. Sequence показывает «как это работает», state — «что бывает с объектом во времени».

### Глава «Развёртывание»
Deployment diagram. Описание узлов, требований к инфраструктуре, процесс deploy.

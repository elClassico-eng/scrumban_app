# Учебный разбор Package диаграммы

Package diagram показывает **из каких модулей собран проект и как они импортируют друг друга**. Это вид на код-базу, а не на доменные сущности (это Class) и не на runtime (это Component).

> **Цель:** после прочтения ты должен уметь:
> 1. Объяснить, что такое package, dependency, стереотип.
> 2. Защищать «модульный монолит» через ацикличный граф зависимостей.
> 3. Читать полную диаграмму [`../package.puml`](../package.puml) и понимать, какой пакет за что отвечает.

## Зачем нужна Package diagram

Отвечает на вопрос: **«Как организован код?»**

- **Class diagram** — какие данные.
- **Component diagram** — какие процессы крутятся в проде.
- **Package diagram** — **какие папки в репо и кто кого импортирует**.

Пакет ≈ папка с `index.ts` или модуль. Один пакет — связная единица: его можно отдельно протестировать, переименовать или (в перспективе) выдрать в микросервис.

Идёт в главу диплома **«Архитектура»** или **«Проектирование»** — рядом с Component diagram, но крупнее зерно (пакет, не функциональный блок).

## Шаг 1 — Минимальный пакет и импорт

**Файл:** [`01-минимальный-пакет.puml`](01-минимальный-пакет.puml)

Три пакета — `app/`, `server/`, `drizzle/` — и стрелки между ними.

### Синтаксис
```plantuml
package "имя" as alias {
  ' содержимое
}

alias1 --> alias2 : "подпись"
```

- **Имя в кавычках** — чтобы можно было использовать слэши и точки (`server/api`, `app/components`).
- **`as alias`** — короткое имя для ссылок в стрелках (без слэшей).
- **Содержимое в `{}`** — другие пакеты или компоненты внутри.

### Что значит стрелка
Стрелка — **направленная зависимость**. `A --> B` читается «A зависит от B» / «A использует B».

В коде это:
```ts
// в файле app/pages/index.vue
import type { User } from '~~/shared/types/auth.d.ts'
```

Если есть импорт — есть стрелка. Если стрелки нет, импорта быть не должно (иначе диаграмма врёт).

## Шаг 2 — Стереотипы

**Файл:** [`02-стереотипы.puml`](02-стереотипы.puml)

Стереотип — это «ярлычок» в `<<...>>`, который добавляет смысл пакету. Технически это просто текст в кавычках-шевронах, но визуально — способ рассортировать пакеты по типам.

### Стереотипы в нашем проекте

| Стереотип | Что значит | Пример |
|-----------|-----------|--------|
| `<<future>>` | Пакета ещё нет, появится в Target | `server/middleware/`, `api.d.ts` |
| `<<library>>` | Внешняя зависимость (npm) | `drizzle-orm`, `zod`, `nuxt-auth-utils` |

### Стрелки сплошные vs пунктирные

| Запись | Семантика | Когда использовать |
|--------|-----------|-------------------|
| `A --> B` (сплошная) | прямой `import` в коде | Доказуемо grep'ом |
| `A ..> B` (пунктирная) | слабая «использует» | DI, события, Target-связь |

Для защиты диплома: **сплошная стрелка = есть `import` в TS-файле**. Если на диаграмме сплошная, а в коде нет — неправда. Лучше пунктирная.

### Зачем `<<future>>` отдельно

Память о claim discipline: «не рисовать то, чего нет». Если на диаграмме `server/middleware/` нарисован как обычный пакет — значит, в репо лежит папка с кодом. Если её нет — `<<future>>` либо вообще не рисуем.

В нашей основной диаграмме мы пошли дальше: Target-пакеты вынесены в отдельный note `N1` снизу, чтобы они не путались с Current. На учебной диаграмме оставили `<<future>>` ради примера нотации.

## Шаг 3 — Ацикличный граф vs цикл

**Файл:** [`03-ацикличность-vs-цикл.puml`](03-ацикличность-vs-цикл.puml)

Главное содержание Package diagram — **направление стрелок**. Граф зависимостей должен быть **ациклическим** (DAG), то есть из любого пакета нельзя вернуться в него же по стрелкам.

### Почему циклы — это плохо
1. **Сборка ломается.** TypeScript-компилятор не сможет вывести порядок типов: A нужен B, B нужен A.
2. **Логика размазывается.** Если db импортирует api, непонятно, где живёт «правда» — в БД-слое или в HTTP-слое.
3. **Тестирование рушится.** Нельзя замокать один слой, не таща за собой весь цикл.
4. **Невозможно вытащить модуль.** Хочешь вынести `services/` в библиотеку или в микросервис — а он завязан на `api/`. Узел не разрезается.

### Наша иерархия (без циклов)
```
app/  →  shared/types

server/api  →  server/services  →  server/db/schema
              ↓
            server/utils

tests/  →  всё остальное (но не наоборот)
```

Стрелка сверху вниз. Никогда снизу вверх.

### Как это контролировать

- **Phase 1-3 (сейчас):** ручной контроль через code review + эту диаграмму.
- **Target:** ESLint-rule `no-restricted-imports` или плагин `eslint-plugin-boundaries` — авто-проверка в CI.
- Альтернатива на будущее: `madge --circular .` (детектор циклов в JS/TS).

## Полная диаграмма — что нового

В [`../package.puml`](../package.puml) видишь всё, что разобрано выше, плюс:

- **Server tier разделён** на `api`, `services`, `db/schema`, `utils` — ровно как в репо.
- **`server/api` имеет вложенность** по реальным URL-сегментам: `auth/`, `workspaces/[id]/`, внутри которых `boards/[boardId]/`, `members/`. Это файл-роутинг H3 — иерархия папок == иерархия URL.
- **8 сервисов перечислены поимённо** — потому что их немного, и видно покрытие доменом.
- **5 файлов schema** — соответствуют 9 таблицам (workspaces.ts описывает и `workspaces`, и `workspace_members`; tasks.ts — `tasks` и `task_events` и т. д.).
- **External npm deps** показаны отдельным пакетом со стереотипом `<<library>>`.
- **Notes снизу** — Target-пакеты с триггерами и acyclic claim.

Не пугайся количества: читай по слоям сверху вниз, как в шаге 3.

## Возможные вопросы на защите

1. **«Чем Package отличается от Component?»**
   «Component — это runtime: что крутится в проде, какие процессы общаются по сети. Package — это compile-time: какие папки в репозитории и кто кого импортирует. Один Component (Nitro server) — это десятки пакетов на Package-диаграмме».

2. **«Почему вы говорите "модульный монолит" — где модули?»**
   «Модули — это пакеты на этой диаграмме. Каждый пакет = одна папка с `index.ts`, у него чёткая ответственность (api — обработчики, services — бизнес-логика, db — схема). Границы заданы импортами TypeScript: попытка импортировать из чужого слоя сломает сборку. То же самое, что микросервисы дают через сетевые API, мы даём через граф импортов — без overhead отдельных деплоев».

3. **«Почему не выделили `server/middleware/` сразу?»**
   «YAGNI. Сейчас auth/tenant/rbac guards — несколько строк в начале каждого handler'а. Извлекать middleware-чейн имеет смысл, когда таких handler'ов накопится 30+ — иначе абстракция дороже дублирования. Триггер задокументирован в note N1».

4. **«Почему `app/` пустой — это же фронтенд-проект?»**
   «Phase 1-3 — backend-first: API, БД, тесты, аналитика. Фронтенд — Phase 4. Это сознательный план: сначала железобетонный API с тестами, потом UI поверх готового контракта. На Phase 4 в `app/` появятся `components/`, `composables/`, `stores/` — они показаны на диаграмме как Target в note».

5. **«Как доказать ацикличность?»**
   «Сейчас — через code review и через эту диаграмму. В Target планируется ESLint-rule (`no-restricted-imports` или `eslint-plugin-boundaries`), который автоматически провалит CI при попытке импортировать из чужого слоя. Также можно использовать `madge --circular` для детекта циклов».

6. **«Почему `tests/` зависит от всего?»**
   «Это нормально для интеграционных тестов: они дёргают сервисы и БД как чёрный ящик. Главное — обратной зависимости нет. Production-код ничего не знает о тестах, и при сборке prod-артефакта `tests/` не попадает в bundle».

## Глоссарий

| Термин | Перевод / пояснение |
|--------|---------------------|
| **Package** | Пакет — папка с кодом, логически связанная единица |
| **Dependency / import** | Зависимость / импорт — стрелка «использует» |
| **Acyclic graph (DAG)** | Ациклический граф — нет путей, по которым можно вернуться в исходный узел |
| **Stereotype** | Стереотип — метка в `<<...>>` (`<<future>>`, `<<library>>`) |
| **Modular monolith** | Модульный монолит — один артефакт развёртывания, но с чёткими внутренними границами |
| **File routing** | Файл-роутинг — структура папок == структура URL (это даёт H3/Nitro) |
| **Layered architecture** | Слоистая архитектура — стрелки идут только сверху вниз |
| **Boundary check** | Проверка границ — линтер ловит запрещённые импорты в CI |

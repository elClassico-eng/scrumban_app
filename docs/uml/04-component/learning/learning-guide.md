# Учебный разбор Component диаграммы

Component diagram показывает **архитектуру системы** — её крупные блоки и как они связаны. Это вид «с высоты» на ПО, не детали кода.

> **Цель:** после прочтения ты должен уметь смотреть на полную диаграмму [`../components.puml`](../components.puml) и понимать, какой компонент за что отвечает.

## Зачем нужна Component diagram

Отвечает на вопрос: **«Из каких больших частей состоит ПО и как они связаны?»**

- Для класс-диаграммы — «из чего состоят данные».
- Для ER — «как устроена БД».
- Для component — **«как устроено приложение целиком на верхнем уровне»**.

Идёт в главу диплома **«Архитектура»** (или «Проектирование системы»).

## Шаг 1 — Один компонент

**Файл:** [`01-один-компонент.puml`](01-один-компонент.puml)

Простой прямоугольник с подписью. Это и есть «компонент».

### Что такое компонент
- **Крупная часть системы**, выполняющая одну большую роль.
- Один компонент может содержать десятки классов, тысячи строк кода.
- В нашей системе: Go Backend, Nuxt Frontend, PostgreSQL, Caddy, Object Storage.

### Отличие от класса
- **Класс** — одна сущность данных (User, Task).
- **Компонент** — программный модуль, большой кусок ПО, который обычно содержит много классов/функций внутри.

### Как рисуют
- Обычный прямоугольник с именем.
- Иногда справа — иконка «две вкладки» (стандартная UML-иконка).
- Мы используем простой вариант.

## Шаг 2 — Взаимодействие между компонентами

**Файл:** [`02-взаимодействие.puml`](02-взаимодействие.puml)

Несколько компонентов + стрелки между ними.

### Что означают стрелки
- Каждая стрелка — связь/зависимость.
- Подпись на стрелке — **что передаётся** (протокол, данные).

### Типичные протоколы на стрелках
- `HTTPS` — защищённый HTTP (для всех публичных запросов).
- `HTTP` — обычный HTTP (внутри доверенной сети).
- `SQL` — запросы к базе.
- `gRPC` — быстрый RPC-протокол (мы не используем).
- `S3 API` — для Object Storage.

### Особые виды компонентов
- `database` — рисуется как цилиндр, используется для БД.
- `cloud` — рисуется как облако, для внешних сервисов.
- `actor` — человек-пользователь, может быть снаружи границы.

Эти «стереотипы» — визуальные метки, чтобы быстро понять природу компонента.

## Шаг 3 — Вложенные компоненты

**Файл:** [`03-вложенность.puml`](03-вложенность.puml)

Большой компонент `Go Backend` **содержит внутри** 4 меньших: HTTP API, Middleware, Services, Storage.

### Зачем вложенность
1. **Zooming**: сначала общая картина (один ящик), потом «заглянуть внутрь».
2. **Граница ответственности**: видно, кто за что.
3. **Тестирование**: можно заменить любой подкомпонент на mock.

### Наши слои в Go Backend
```
HTTP API        ← принимает запросы (echo)
    ↓
Middleware      ← проверяет cookie, права, RLS
    ↓
Services        ← бизнес-логика
    ↓
Storage         ← общение с БД
```

Стрелка идёт **только сверху вниз**. Это правило: нижние слои не знают о верхних. Если его нарушить — получится «каша». Мы проверяем правило инструментом `go-arch-lint` в CI.

### Другой пример вложенности
Nuxt Frontend тоже «декомпозируется»:
- Pages (маршруты страниц).
- Components (переиспользуемые блоки).
- Stores (Pinia — глобальное состояние).
- API Client (обращения к Backend).

## Шаг 4 — Упрощённая архитектура системы

**Файл:** [`04-полная-упрощённая.puml`](04-полная-упрощённая.puml)

Это **упрощённая версия** нашей архитектуры: все компоненты видны, но без внутренней детализации.

### Читаем по порядку
1. **Пользователь** — человечек слева.
2. **Browser** — клиент, в нём работает Nuxt SPA.
3. **Caddy** — reverse-proxy, принимает HTTPS и решает куда.
4. **Nuxt static** — набор HTML/JS/CSS.
5. **Go Backend** — основной сервер.
6. **PostgreSQL** — всё хранится здесь.
7. **Object Storage** — для файлов.
8. **Внешние сервисы** — Telegram, GitFlic и т. д.

### Ключевые наблюдения
1. **Caddy — единая точка входа.** Всё HTTPS идёт через него.
2. **PostgreSQL — единый источник правды.** Никакого отдельного Redis или Kafka в MVP.
3. **Object Storage отделён.** Файлы не лежат в БД — так правильнее для масштабирования.
4. **Backend общается с внешним миром.** И исходящий трафик (уведомления), и приём webhook'ов.

## Полная диаграмма — что нового

Откроем [`../components.puml`](../components.puml) в IDE. Там всё, что мы обсудили, плюс:

- **Nuxt Frontend разделён** на static bundle + server (BFF).
- **Go Backend имеет много внутренних компонентов**: HTTP API, Middleware chain (Logging → AuthN → Tenant → RBAC), Services (Workspace/Project/Task/Sprint/Auth), Analytics Engine (CFD/Monte Carlo/Little's Law), Event Bus, SSE Hub, Background Worker (river), Feature Flags, Storage.
- **PostgreSQL** тоже декомпозирован: Domain tables, events, aggregates, river queue, LISTEN/NOTIFY.
- **Стрелки подписаны** конкретными протоколами и типами взаимодействия.

Не пугайся количества — читай по слоям сверху вниз, как в шаге 2.

## Возможные вопросы на защите

1. **«Почему Caddy, а не Nginx?»**
   «Caddy автоматизирует HTTPS через Let's Encrypt без настройки. Config проще и читаемее. Для MVP достаточно, для scale — не уступает Nginx».

2. **«Почему модульный монолит, а не микросервисы?»**
   «Solo-разработчик, микросервисы удваивают объём работы (деплой, мониторинг, API-контракты между сервисами). Модульный монолит даёт те же чёткие границы через пакеты Go + дисциплину импортов, но без overhead».

3. **«Зачем Object Storage, почему не хранить файлы в БД?»**
   «БД дорогие в масштабировании. Файлы — большие и read-only; S3-совместимое хранилище намного дешевле и быстрее. Бонус: backup проще».

4. **«Зачем LISTEN/NOTIFY между компонентами backend'а?»**
   «Для event-driven подхода: когда в одном инстансе Go-бэка происходит событие, другие инстансы должны узнать (например, SSE-клиенты, подключённые к соседним нодам). LISTEN/NOTIFY — встроенный в Postgres механизм pub/sub; не нужен отдельный Redis».

5. **«Почему разделение на слои внутри Backend?»**
   «Чистая архитектура: каждый слой знает только о нижестоящем. HTTP API не трогает Postgres напрямую — только через Services и Storage. Это упрощает изменения и тесты».

## Глоссарий

| Термин | Перевод / пояснение |
|--------|---------------------|
| **Component** | Компонент — крупная часть системы |
| **Interface (provided/required)** | Интерфейс — контракт взаимодействия компонентов |
| **Dependency** | Зависимость — стрелка «использует» |
| **Composition (containment)** | Вложенность — один компонент содержит другие |
| **Reverse proxy** | Прокси-сервер, принимает внешние запросы и маршрутизирует |
| **BFF (Backend For Frontend)** | Тонкий слой между фронтендом и backend'ом, агрегирует/адаптирует |
| **Modular monolith** | Модульный монолит — один артефакт с чёткими внутренними границами |
| **Middleware chain** | Цепочка middleware, которые обрабатывают запрос по очереди |
| **Event bus** | Механизм публикации и подписки на события внутри системы |
| **Stereotype** | Метка компонента (`<<frontend>>`, `<<backend>>`, `<<database>>`) |

Архитектура Scrumban документируется в **two-track** формате в каждом spec-документе.

**Track 1 — Current MVP (что строим сейчас):**
- Максимально простые решения, которые user понимает и может реализовать соло.
- Минимум новых концепций (5 для старта, по 2–3 на этапе).
- Каждый выбор — «достаточно хорошо, чтобы работать».

**Track 2 — Target architecture (куда эволюционируем):**
- Production-grade идеал: RLS, event sourcing, pub/sub, precomputed aggregates, contract testing, feature flags, observability, горизонтальное масштабирование.
- То, что было в «senior-level design» (секция 3 v1 до упрощения).
- Показывает архитектурную зрелость и служит материалом для главы «архитектура и перспективы развития» диплома.

**Track 3 — Evolution path (как идём из Track 1 в Track 2):**
- Точные триггеры: «когда пользователей станет X — переходим на Y».
- Какие части переписываются, какие остаются как есть.
- Что можно отложить навсегда, если не понадобится.

**Why:** Пользователь явно попросил сохранить «идеальную» архитектуру как цель, к которой движемся шаг за шагом. Это и педагогически правильно (учится постепенно), и академически сильно (показывает понимание эволюции систем), и практически безопасно (не застрянет в ранних решениях, зная куда целиться).

**How to apply:** 
- Каждый MD-документ в docs/ имеет три раздела: Current / Target / Evolution.
- Введение новой концепции (RLS, event sourcing, pub/sub) оформляется как «Будет в Phase X; триггер — Y; предварительная замена — Z».
- При каждом архитектурном решении явно фиксировать: это временное упрощение или финальное решение.
- В диалоге: когда user внедряет что-то из Track 2, я напоминаю «это шаг к зафиксированной target-архитектуре, предусмотренный в таком-то документе».

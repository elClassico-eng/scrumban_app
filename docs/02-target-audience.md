# 02 — Target Audience

## Основной сегмент

Русскоязычные IT-команды средне-крупного размера (**30+ человек**), работающие по гибким методологиям (Scrum, Kanban, гибрид). Типичная структура — одна продуктовая компания или R&D-подразделение, разбитая на 3–5 sub-команд (2–8 человек каждая) с общими процессами доставки.

Географически — преимущественно Россия и СНГ, но продукт по умолчанию мультиязычный (RU/EN) с расчётом на русскоязычные команды в других странах.

## Первичная персона: Scrum Master / Agile Coach / Delivery Manager

Тот, кто **принимает решение о внедрении инструмента** и использует его чаще всех. Ему платят за то, чтобы процесс работал.

### Типичный портрет
- **Роль:** Scrum Master / Agile Coach / Delivery Manager / Head of Engineering.
- **Компания:** IT-компания или IT-подразделение, 30–200 человек.
- **Опыт:** 3–8 лет в управлении проектами; хорошо знает Scrum, Kanban, метрики, имеет сертификации (CSM, PMI-ACP или аналоги).
- **Вовлечённость в инструменты:** сам настраивает доски, отчёты, дашборды; не будет использовать то, что не умеет управляемо конфигурировать.

### Ключевые цели (Jobs to be Done)
1. **Видеть здоровье процесса в реальном времени** — не «раз в спринт на ретро», а в любой момент.
2. **Предсказывать доставку** — сколько историй завершится к концу спринта, с какой вероятностью.
3. **Выявлять bottlenecks** — где застревают задачи, какие колонки перегружены.
4. **Обосновывать управленческие решения данными** — «WIP-лимит в 5 выбран, потому что…» (не «потому что я так решил»).
5. **Помогать командам расти** — показывать тренды, сравнивать спринты, выявлять регрессы.

### Боли, которые существующие инструменты не закрывают
1. **Burndown недостаточен.** Показывает только остаток по story points, не проливает света на причины отклонений.
2. **Нет нормального CFD из коробки.** В Jira настраивается плагинами; в Kaiten — есть, но без прогнозов; в YT — упрощённый.
3. **Нет вероятностных прогнозов.** Все отчёты детерминированные: либо «успеет», либо «не успеет», без shades of grey.
4. **Рекомендации по WIP — либо отсутствуют, либо «поставьте 3 и посмотрите».** Нет обоснования математикой.
5. **Анализ требует выгрузки в Excel.** Многие Scrum Master'а ведут «свою аналитику» в таблицах, потому что встроенной не хватает.

### Что продаст продукт этой персоне
- **CFD по умолчанию с первого дня** — без плагинов и настройки.
- **Monte Carlo прогноз «спринт будет закрыт с вероятностью 78%, P95 = на 2 дня позже»** — цифра с доверительным интервалом, не бинарная.
- **Little's Law рекомендация «WIP=5 оптимален, потому что throughput=10/нед и cycle=3.5д»** — с объяснением.
- **Scatter plot cycle time с percentile-based алертами** — сразу видно застрявшие задачи.
- **Всё это встроено, не конфигурируется плагинами.**

## Вторичные персоны (учитываем, но компромисс в их пользу не делаем)

### Team Lead / Engineering Manager
**Цель:** оперативное управление командой. Кто чем занят, где блокеры, когда будет X.

**Наш подход:** базовый функционал доски и задач покрывает их потребности без специального UX. В аналитике им интересен бэкограундный «прогноз доставки», но они не ходят глубоко в CFD.

### Разработчик / Тестировщик (обычный член команды)
**Цель:** видеть свои задачи, понимать приоритеты, не тонуть в церемониях.

**Наш подход:** основной UI доски остаётся простым и быстрым. «Мой список задач», фильтры, простая навигация. **Не перегружаем** базовый экран аналитикой — она живёт в отдельной вкладке для тех, кому нужно.

### CTO / PMO / Head of R&D
**Цель:** портфельная аналитика на нескольких командах, predictability на уровне организации.

**Наш подход:** в MVP нет кросс-командных view'ов (**LATER**). В target-state — отдельный раздел «портфель» для сравнения команд и сводных метрик.

## Антипаттерны ЦА (кто НЕ наша аудитория)

- **Команды 2–5 человек, не использующие Scrumban.** Для них переусложнение — подойдёт YouGile, Trello.
- **Enterprise 500+ со сложными cross-team-процессами** и строгими политиками безопасности на уровне всей корпорации. Для них — Jira Data Center, Yandex Tracker Enterprise (после защиты диплома можем целиться, но не в MVP).
- **Не-IT команды** (маркетинг, HR, поддержка). Scrumban-ориентированные фичи им не нужны.
- **Фрилансеры и частные лица.** Другая история (tasks, не process).

## Гипотеза готовности платить

- **Scrum Master'ы в компаниях 30+** — типичный decision-maker, имеют бюджет на PM-инструменты (1000–3000 ₽/пользователь/месяц сопоставимо с Kaiten / Yandex Tracker).
- После ухода Jira из РФ сегмент активно ищет замену; заказчики рассматривают **новые продукты**, если они решают их задачу.
- Продукт с ярко выраженной фокусом («именно для Scrumban, именно с нормальной аналитикой») легче продавать, чем «ещё один таск-трекер».

## Dual-track: как ЦА расширяется по фазам

### Current (MVP)
Только Scrum Master персона, одна команда-заказчик (мы сами используем для диплома), данные для демо — синтетические + реальные из тестовой команды.

### Target
Три персоны обслужены (Scrum Master — primary, Team Lead / разработчик — secondary), 3–5 тестовых компаний-клиентов к моменту защиты. Данные для research-эксперимента собраны на реальных командах.

### Evolution
Через 2–4 месяца после MVP: открытое бета-тестирование для 10–20 команд, сбор обратной связи. Через 6–9 месяцев: платный запуск, первые paying customers. Расширение на CTO/PMO персону (портфельный view) — Phase 3.
